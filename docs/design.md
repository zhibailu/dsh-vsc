## 1. 先把领域从零讲清楚

这一节不带任何滤镜，就是最朴素的概念。你不需要会写代码，只需要愿意接受几个比喻。

### 1.1 什么是 DSH（DeepSeek Harness）

DSH 是一个**本地的 AI 智能体（agent）服务**。

「智能体」在这个语境下 = 一个 AI，它不只是跟你聊天，还**会动手干活**：改文件、跑命令行、查资料，一步步完成一个任务。DeepSeek Harness（简称 DSH）就是干这个的东西，它跑在你自己的电脑上，默认在 `http://127.0.0.1:3080`。

可以把它理解成：**一个住在你电脑里的、会做事的 AI「工人」**。

### 1.2 它是「服务」，不是一个应用

关键认知：DSH 不止是一个你能双击打开的软件，它更像一台**服务器**。它对外提供两样东西：

- **一个 RPC 接口**（`POST /api/<method>`）：你叫它干活、问它状态，走这个。
- **一条实时事件流**（`/api/events.mux`）：它干活的过程——用了哪个工具、改了哪些文件、说了什么——以一条条带序号（seq）的「事件帧」持续推给你。

这两样合起来，就是 DSH 和「外面的人」交流的全部方式。

### 1.3 什么是「协议」——你和 DSH 说话的方式

DSH 说一种**约定的“语言”**，官方把它定义得很清楚（官方 README 原文就叫它"wire contract"，协议契约）。这语言一共四种消息：

| 消息 | 谁发起 | 走哪 | 干什么 |
|---|---|---|---|
| `ClientRequest` | 客户端 → 服务端 | `POST /api/<method>` body | 你叫它干活 |
| `ServerResponse` | 服务端 → 客户端 | 那个 POST 的 body | 告诉你结果 |
| `ServerRequest` | 服务端 → 客户端 | 事件流里的帧 | 它反过来**问你**（比如「要不要允许这个操作？」） |
| `ClientResponse` | 客户端 → 服务端 | `POST /api/respond` body | 你回答它的问题 |

**铁律**：每次回应都**原样带回请求方的 `rpcId`**，绝不自己造一个新的。这是对账的依据。

> 一句话：**协议就是「双方都认的那套约定」**。谁按这套约定来，谁就能跟 DSH 顺畅交流，不管你是浏览器、命令行，还是别的什么。

### 1.4 什么是「桥接」——为什么是「第二个客户端」

DSH 自带一个**网页界面（Web GUI）**。那个网页，本质上就是 DSH 的**第一个客户端**——它用上面那套协议跟 DSH 说话，把聊天框、工具调用、事件流画出来给你看。

**这就是整个项目的核心洞察**：

> 网页能做的所有事，靠的只是「那套协议」。既然协议是公开约定的，那我**也能**用同一套协议做一个客户端——**不必是网页，可以是 VS Code 侧边栏**。

于是这个项目「链接」了 DSH 和 VS Code，但它**没有重写 DSH**，也没有**另起一个 DSH**。它只是**多了一个看懂 DSH 协议、并把内容用 VS Code 的方式呈现出来的“客户端”**。

这就叫**桥（bridge）**：一脚踩在 DSH 的协议这一端，一脚踩在 VS Code 这一端，中间只传话，不改 DSH 本体。

> 为什么是「第二个客户端」而不是「第二个服务端」？这是有血泪教训的，见 §4.1。

### 1.5 什么是「插件框架」——官方 UI 是怎么长出来的

DSH 的官方网页界面，不是一张死页面。它是一个**运行时（runtime）+ 一堆插件**组成的框架：

- **runtime**：管加载、管连接、管把消息路由给谁。
- **插件集**：会话列表、聊天框、工具栏、设置页……这些 `client-ui-*` 都是独立插件，只属于官方的 runtime。

官方 UI 每次「换了个样子」，本质上是**插件集更新了**（插件整体升级换代）。

这就是 §3.3 的关键铺垫：**UI 是容易变的，协议是稳定的。**

## 2. 这个项目的定位

### 2.1 一句话定位

> **它是 DSH 的一个「好客户端」——只做协议对岸的翻译，不碰 DSH 的本体。**

它把 DSH 的**真实能力**（会话、模型、工具、审批、提问）用 VS Code 的方式重新呈现，同时**保留** DSH 最珍贵的东西：**一份历史、一套契约、官方本体一行都不改**。

### 2.2 三条边界（不做什么，以及为什么）

| 不做 | 为什么 |
|---|---|
| **不重写 DSH** | 官方本体是「字节级一致」的（npm 发布原版）。它多稳，你就多稳；它升级，你不用跟着大改。 |
| **不复制/模仿官方 UI 框架** | 模仿框架＝替官方再维护一遍插件系统，既不讨好官方，也累死自己。 |
| **不另起第二个 DSH** | 两个 DSH 共用一份历史日志，会互相写坏（这是真实踩过的坑，见 §4.1）。 |

守住这三条，才谈得上「纯桥接」。

## 3. 灵魂的四块拼图

这四块，就是这套设计最硬核、也最难被别人复制的部分。**它们共同证明：这不是一个「把网页塞进侧边栏」的取巧实现，而是一个真正的协议级客户端。**

### 3.1 拼图一：HarnessClient —— 只有约 200 行

`src/harness/client.ts` 是整套桥接里最核心的一个文件，**只有约 200 行**。它是官方浏览器端「client-runtime」的一个**最小 Node 移植**：

- 实现的是**和浏览器完全相同的协议**；
- **不 import 任何 DSH 内部包**；
- 只要 Node ≥ 18（`fetch` 是全局的）就能跑。

行数少不是偷懒，而是**它足够薄**。官方把「协议的所有不变量」都封装在客户端基类里（`AbstractApiClient`），子类只需要提供一个 `doFetch` 传输。我们这 200 行就是在 Node 里把这套协议重新最小实现了一遍。

> **价值**：别人写一个「DSH 插件」，要先读懂官方整个插件框架。你写一个「DSH 客户端」，只需要读懂**协议本身**。前者重，后者轻；前者跟着 UI 变，后者跟着契约走。

### 3.2 拼图二：PanelEvent —— 原样转发，不做重新建模

`src/panel/protocol.ts` 里的 `PanelEvent`：

- 它**几乎就是** DSH 推来的原始事件帧 —— 类型、序号、时间、数据原样带过来；
- 面板拿到的是一个**未经二次加工的原始帧**，**渲染层的解释由面板自己完成**；
- **桥接层在中间不做任何「重新建模」**，不把事件改造成另一套自己发明的结构。

> **价值**：桥接层越「透明」，越不容易跟官方语义脱节。官方一个事件是什么意思，我们这里还是什么意思。这叫**无损**——信息在桥这头到那头，一个字节都没被自作主张地改造。

### 3.3 拼图三：消费同一份协议契约 —— 官方 UI 怎么变我都不怕

这是整套设计最值钱的地方。

DSH 官方界面 = **runtime + 插件集**。官方每换一次 UI，本质是**插件集整体换新**。而我们的项目：

> **消费的是协议契约，不是官方 UI。** 只要协议不变，官方 UI 无论怎么改版、插件怎么疯狂升级，我们都**不需要跟着改**。

——因为**协议是官方向客户端承诺的契约**（"wire contract"），它是稳定的；而**UI 只是这份协议的一种消费方式**，它是会变的。

更有意思的是，官方 README 明确写了：

> "No protocol version field — client and host ship together; `host.describe` gains a version negotiation field **only when an independently released client exists**."

这句话等于官方**亲口承认**：他们原本的模型是「客户端和 DSH 一起发布」，所以不需要版本协商字段；**要等到出现一个独立发布的客户端，才有必要加**。（官方 UI 和自己绑死发布，自然不会变更；有了我们这种第三方，才有协商的必要。）我们正是那个**独立发布的第三方客户端**之一——所以这套「协议优先、UI 无关」的立场，恰好踩在官方为“未来的独立客户端”预留的轨道上。

> **一句话**：**我们站的不是「UI 这一层」，而是「协议这一层」。** 协议稳，则我们稳；协议变，那才是唯一需要适配的信号。这正是「无损扩展」的真身。

### 3.4 拼图四：overlay —— 唯一的「临时侵入」，且被严格隔离

这是四块拼图里**唯一不是纯协议**的一块。

有 4 个能力，DSH 的协议**没有暴露**（比如「现在有几个客户端连着」「工具执行时不弹黑色控制台」），但这 4 个能力对我们**切实有用**。官方不提供接口，我们只能**垫一个临时补丁**。

它不是插件，是**对官方进程内部的一次临时侵入（monkey-patch）**。详见下一节——怎么让它「侵入」得可控、可回滚、绝不坏事。

## 4. 唯一的「越线」：overlay（诚实面）

这一节是别人最容易质疑你的地方：**「你既然标榜纯桥接，为什么还是动了官方？」** 你要主动、诚实、有理有据地讲清楚。

### 4.1 它是什么，为什么存在

DSH 有一套**运行时补丁机制（overlay）**，一共 4 个 delta，作用在官方进程**加载模块的瞬间、在内存里**：

| delta | 作用 | 为什么需要 |
|---|---|---|
| `clientCount` | `host.describe` 多返回一个「当前客户端数」 | 它判断「**是不是最后一个客户端在关**」，用来决定关 VS Code 时要不要顺手停掉自拉的 DSH，而不是把正在被别人用的 DSH 杀掉。 |
| `windowsHide` | 启动子进程时隐藏窗口 | 免得 DSH 跑工具时在桌面**弹出一排黑窗口**。 |
| ACL 控制台 ×2 | 隐藏受限令牌子进程的控制台 | 同上，弹窗太吵。 |

**谁发明了这个机制的？** 不是凭空想的，是**踩坑踩出来的**。2026-08 发生过一次真实事故：扩展自拉了一个 DSH（3081 端口），和网页端的 DSH（3080 端口）**共用同一份 `~/.dsh` 历史目录**。两份日志没有跨进程锁，两个进程各自的内存序号交错排写，结果日志被写坏（`corrupt session log: seq gap`）。

修复方向就一个字：**不让你抢**——**扩展只做「第二个客户端」，绝不做「第二个服务端」**。只有确实没有任何 DSH 在跑时，才自拉一个兜底，并且用「引用计数」来关它（最后一个客户端走了才停）。

但「引用计数」需要知道「**现在有几个客户端连着我**」，而协议**没有暴露这个数**。这就是 `clientCount` 补丁的来历——**协议做不到的事，用补丁兜底**。

### 4.2 为什么它被允许：三条安全护栏

补丁危险，所以给它上了三把锁：

1. **内存篡改，不碰磁盘**：补丁在官方模块**加载进内存的一瞬间**换掉源码，**磁盘上的官方文件全程只读、一行不改**。进程退出，补丁就消失。官方安装树始终是「字节级一致」的 npm 原版。
2. **SHA 校验，不对就整体放弃**：启动时校验官方文件的 SHA256，万一跟 npm 发布版对不上（官方升级了、被别人改过），**整个补丁跳过**，进入降级模式——绝不硬着头皮去 patch 一个不认识的文件。
3. **金丝雀锚点，变了就退**：哪怕 SHA 通过了，patch 前还要确认「官方源码里我认识的那几行还在」。找不到，就记一条 `CANARY-FAIL`，**放弃这次补丁**，正常降级跑。

> 降级后最坏会发生什么：`clientCount` 变成 `undefined`，关闭逻辑退回「自拉的实例无条件停」；窗口隐藏失效，工具执行可能弹个控制台。**都不致命。**

### 4.3 它的「退出条件」

这套补丁是**一次性的临时解决方案**，有明确的退役标准：

> **等官方自己实现了这些能力，就删掉对应 delta，改用官方字段。** 官方 README 里已经预留了 `hostInstanceId`（服务端进程身份位，`documented reservation`），这说明官方**已经意识到**「客户端身份/连接关系」这类需求迟早要开接口——只是现在还没实现。等真的落地了，我们的补丁就该退役。

到那一天，overlay 整个被移除，项目就真正做到 100% 纯协议、零侵入。

**所以对外你可以理直气壮地说**：我们只在一处「越线」，而且那处是被逼的、有护栏的、有退役路线的——**其余全是协议，一分不少。**

## 5. 谁认可你（以及你为什么可能想错了）

「这没贴官方理念，认可度打折扣」——这是你的担心。我们换个角度：**先问“被谁认可”。** 不同的认可方，看的是完全不同的东西。

### 5.1 官方 DSH 认可你什么

官方最看重的是：**你尊重我的协议、不改我内部、做得很薄很稳。**

- 一个 **200 行的协议客户端 + 自己画的界面**，比一个**模仿插件框架的壳**更让官方喜欢——因为后者是在「重新发明人家的轮子」，前者是在「**真正用人家给的路**」。
- 而且你**给协议提供了一个真实的使用场景**。官方本来以为不会有第三方客户端（见 §3.3 引用），你恰恰证明了「这套协议可以支撑一个独立客户端」——**这本身就是对官方生态的贡献**。

### 5.2 社区用户认可你什么

用户不关心架构形制，他们关心两件事：

- **开箱即用**：装了就能用，不用装一堆东西，不用重输 API key。
- **界面质量**：看起来顺手、干起活来清晰。

我们两者都占了——`dsh-vsc` 是原生 VS Code 面板 + 编辑器右键提问，不是塞一个浏览器 iframe 完事。

### 5.3 架构审视者认可你什么

真正懂架构的人，看重的是**能不能立得住**这三个词：

1. **接口稳定**：协议契约不动，你我就不慌。
2. **关注点隔离**：协议层、渲染层、侵入层（overlay）分得清清楚楚，各管各的，互不污染。
3. **组合优于继承**：不硬造一套「插件框架」去套，而是用「协议总线 + 单元」这样的组合方式，自然生长。

这些**正是插件框架的实质**。我们用**文档 + 边界**证明了同样的实质，而不用真的去造一个框架。

> **结论**：你担心的「模仿」问题，其实是把「**模仿UI**」和「**遵从协议**」混为一谈了。我们遵从的是更底层、更本质的那一层。

1. **它是什么**：一个把「AI 工人 DSH」接进 VS Code 的插件，你在侧边栏里跟 AI 协作改代码。
2. **它怎么实现的**：读懂 DSH 的协议，当它的一台“好客户端”，原样转发它推来的事件，再画成 VS Code 界面。
3. **它凭什么稳**：只碰协议、不碰 DSH 本体；官方界面随便改版都跟我无关；唯一一处动内部的地方也被 SHA 校验和安全护栏圈死了。

## 7. 你可能被问到的问题

**Q：你这不是模仿官方插件框架吗？**
A：不是。模仿框架是「重新发明官方那套插件系统」，那既重又容易跟官方脱节。我做的是「**遵从官方的协议契约**」——这比模仿 UI 更本质。官方 README 自己都说「不会有独立客户端」，我恰好就是第一个证明「可以有」的人。

**Q：你说不动官方，那那几个补丁是什么？**
A：那是唯一越线的地方，4 个 delta，**只为了拿协议没暴露的两个能力**（客户端计数、隐藏控制台）。而且有 3 层护栏：只在内存里改、SHA 不对就整体放弃、锚点找不到就降级。官方文件全程只读。等官方补上接口，这些全删。

**Q：DSH 一升级你会不会坏？**
A：要看升的是哪层。**升级 UI（插件集）→ 跟我无关**，因为我消费的是协议不是 UI。**升级协议（契约）→ 那才是唯一需要适配的信号**，而且只有一处（overlay 的锚点）需要核对。

**Q：为什么不直接把官方网页嵌进侧边栏就行？**
A：做是可以，但那是「壳」，不解决「你选中代码要问 AI」这类 VS Code 原生交互。真正的价值在**原生桥**：编辑器右键提问、工具改动实时计数、审批/提问卡片——这些只有做一个协议客户端才能拿到。

**Q：那 API key 呢？**
A：不用在插件里配。key 在 DSH 那边存着，我只是它的一个客户端，**不碰你的 key**。

### 8.1 术语表

| 术语 | 解释 |
|---|---|
| **DSH** | DeepSeek Harness，本地 AI 智能体服务，默认 `127.0.0.1:3080` |

| **客户端 client** | 用协议跟 DSH 说话的一方（网页 / 本扩展 / 命令行） |

| **mux 事件流** | `/api/events.mux`，实时事件通道 |
| **projections（投影）** | 随历史尾页/实时推送的「当前状态快照」（todos、permissions、title…） |
| **agent preset** | 一个「会话模式/工具组合」的标准模板（标准 / PTC / 极简 / 创造） |
| **overlay** | 运行时内存补丁机制，唯一越线处，有护栏 |
| **pure bridge（纯桥接）** | 只做协议对岸翻译、官方本体一行不改的设计原则 |
