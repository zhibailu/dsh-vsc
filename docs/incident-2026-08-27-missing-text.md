# 事故现场记录：流式文字缺失 + 漫长的兜圈子复盘（第三个复盘文档）

- 日期：2026-08-27
- 范围：`src/panel/native/panel.html`
- 结论：已修复并提交（`2eeac09`、`4ea403a`），诊断工具 `scratch/auto-test.mjs`（jsdom 模拟 webview）保留

---

## 一、现象

在**实时流式**渲染时，assistant 消息的文字（正文）不显示：卡片只有「▸ 思考」折叠栏（或完全空白 + 复制按钮），正文缺失；**reload 后（历史重放）完全正确**。同时期的连锁问题：合并语义反复被改错（动作33 → 一堆动作1 → 反复）、动作组后跟着带复制按钮的空行、用户输入出现两个相同气泡。

## 二、行为轨迹（如实记录，含全部失败尝试——本事故的核心是「兜圈子」）

1. **第一轮（contentBlocks 过滤 + splice + reuse）**：为修「空行+复制」在 `assistant/message` 加空块过滤、空项移除、复用 streaming 项。结果：**没有解决文字缺失**，反而在数据折叠层引入了新的对象生命周期问题。
2. **第二轮（组 key 反复横跳）**：误解「如果下个执行依然是动作那就合并」——先实现全回合合并（动作33 + think 全堆组后，用户：惨不忍睹）→ 再改成每工具一组（一堆动作1，用户：合并被毁）→ 再改回 → 用户明确「相邻才合并、think 是分隔、空步骤不打断」才最终收敛。**这里浪费了大量轮次，因为我没有在改之前把语义问清楚，而是反复猜测。**
3. **第三轮（大量探针）**：加了 amsg / ver-skip / dom-final / as-render / ext-in 等一堆诊断，从「事件丢失」一路排查到「version 机制不可靠」——**方向其实接近了，但全部依赖用户 reload + 跑一轮 + 反馈来观测，每轮成本极高，且探针本身可能干扰时序。**
4. **第四轮（回退基线）**：用户确认「commit 版流式正常」后，`git checkout` 回退到 4256996 并逐项回退我的改动——**仍然复现**。这个结果当时被错误解读为「与我无关」，实际是遗漏了真正的渲染层 bug（见根因 1）。
5. **第五轮（自动化测试，收敛点）**：搭建 `scratch/auto-test.mjs`——用 jsdom 模拟 webview，把**真实事件流**喂进 panel 渲染器（流式模式：逐事件 + 每帧渲染），直接检查最终 DOM。**从此不再需要用户 reload 测试**，一分钟内可复现/验证。批量模式文字正常、流式模式文字缺失——精确复现了用户看到的差异，然后用插入探针定位到 `syncAssistantEl` 新建节点插入被跳过。
6. **最终修复**：`syncAssistantEl` 新建节点必须插入（见根因 1）+ 状态驱动同步 + turn/end 后放行一次渲染 + send 时 history 增量合并；随后两个小问题（空行、重复气泡）也在 auto-test 里验证修复。

## 三、根因总结（最终定位，均有 auto-test 验证）

1. **文字缺失（主根因，commit 版固有）**：`syncAssistantEl` 渲染 block 节点时，位置跳过判断 `node.nextSibling === ref`。新建 body 节点 `nextSibling` 为 `null`，追加到末尾时 `ref` 也是 `null`，`null === null` 误判「已在正确位置」→ **跳过插入 → body 节点永远游离在 DOM 外**。流式时序下 reasoning 恰好是最后一个子节点即触发；reload 时 DOM 状态不同所以正确。
2. **合并语义反复错**：实现前未确认语义，反复在「全回合合并」与「每工具一组」之间横跳；正确语义（用户原话）：相邻工具才合并、think 是分隔符、无内容的空步骤不可见且不打断。
3. **空行**：无内容的步骤（`assistant/message` 只有 tool-call 块）被渲染成空卡片 + 复制按钮——plan builder 跳过即可。
4. **重复气泡**：`send()` 乐观插入 pending 用户气泡；send 后 history 增量重放（修复 5 引入）会让 `turn/start` 插到 pending 气泡之后，`user/message` 只匹配**末尾** pending → 找不到 → 又 push 一个新气泡。修复：匹配任意 pending 气泡。

## 四、最终方案（现行代码）

- **`syncAssistantEl`**：`wasNew` 标记，新建节点无条件 `insertBefore`；位置跳过只用于复用的旧节点。
- **状态驱动同步**：非冻结（当前回合）的 assistant/tool 每次渲染都从最新 state 完整重同步，**去掉 version 跳过优化**——向 web 官方（React 状态驱动）靠拢，根除「version 与内容脱节 → 永久跳过」这一类问题。
- **`turn/end` 后放行一次渲染**（`dirtySync`）：rAF 合并可能把最后一批 text-delta 的渲染延迟到 frozen 边界之后，放行一次避免文字定格在流式中途。
- **send 时 history 增量合并**：live 回合进行中，send 触发的 history 刷新不清空已累积 items，按 seq 去重增量合并（避免重置杀掉流式中内容）。
- **空步骤跳过 + 不打断合并**；**`user/message` 匹配任意 pending 气泡**。
- 所有 TEMP 探针已删除；`scratch/auto-test.mjs` 保留（jsdom + 真实事件流，可无限自测）。

## 五、教训：为什么这次兜了这么大的圈子（对 AI 协作者）

1. **观测手段必须先于修改**。整个事故里大部分轮次都是在「看不到面板真实 DOM」的情况下盲改。CDP 不可用、日志快照抓的是冻结/中间态 DOM，唯一可靠的观测是**用户的眼睛**——于是每改一次都要用户 reload + 反馈，摩擦极大。**最终收敛靠的是搭建 jsdom 自动化测试，把「看 DOM」变成「读输出」，一分钟内可复现、可验证。** 遇到底层渲染问题，第一件事应该是建可观测的自动化测试，而不是改代码。
2. **过早宣布成功 = 幻觉**。多轮「修好了」都是基于回合**进行中**的探针数据或局部指标，而不是最终完整状态——用户每次都被错误结论消耗耐心。**结论必须基于「回合结束后 / 自动化验证后的最终状态」，且说「不确定」比说「修好了」诚实得多。**
3. **基线对照**。用户说「commit 版流式正常」是最早、最强的诊断信号，但直到回退才真正做 `git diff` 对照——如果第一次「文字缺失」时就对照 commit 版渲染路径，主根因（新建节点插入跳过，commit 版固有）会更快暴露。
4. **用户说「reload 后正确」是极重要的信号**：重放路径正确 / 实时路径错误，差异就在两条路径的时序与 DOM 状态——auto-test 的「批量 vs 流式」模式正是复现这一差异的关键。
5. **一次只引入一个改动**：修「send 竞态」时引入「重复气泡」（增量合并打破了 pending 匹配），因为没有把改动控制在最小并同步验证副作用。每次改动后跑一遍 auto-test（含正常/边界场景）可以立刻发现回归。
6. **web 官方是答案**：官方 `dsh-client-ui-conversation` 是 React 状态驱动（每次 state 变化全量重渲染），从不出「版本跳过卡死」这类问题。手写 DOM 同步时，**「少优化、多同步」比「聪明地跳过」更可靠**。
